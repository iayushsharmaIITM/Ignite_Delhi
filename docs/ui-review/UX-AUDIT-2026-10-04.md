# UI/UX audit — served React app (2026-10-04)

Lens: `ui-ux-pro-max-skill:ui-ux-pro-max` (8-pillar priority table + the §1–§3
CRITICAL checks), measured against the project's own **`DESIGN.md`** contract rather
than a recommended style — the repo already owns its design system, so its rules are
the standard and the skill supplies the check categories.

Method: the **committed bundle** was served by a local mock tier (`:8025`,
`PROVIDER=mock`, `AUTH_MODE=off`, `KESTREL_UI=react`) and driven in a real browser at
1440×1000 and 390×844, computing contrast in-page against each element's *actual
painted ancestor background*. The measurement script was a throwaway in `/tmp`; it is
not committed, because a UI-contrast gate needs the app's own theme fixtures before it
can be trusted to stay green.

Not covered: signed-in Clerk UX, streaming feel, and anything requiring the cloud
brain — none of those are reachable without the owner's session.

## What measured clean

| Check | Result |
|---|---|
| Horizontal scroll at 390px | none — `scrollWidth 390 == clientWidth 390` |
| Body-text contrast (WCAG 4.5:1) | **0 failures of 32** painted text nodes |
| Icon-only controls without a label | **0** — every unlabeled control carries `aria-label`/`title` |
| Heading hierarchy | one `h1`, no level skips |
| Reduced motion | honoured — 2 `prefers-reduced-motion` blocks in the served CSS, source `frontend/src/index.css:135` |
| Keyboard focus ring | visible on **11 of 11** controls the keyboard reaches, via `box-shadow` and/or `outline` in `--accent`. Gated in `check_ui_react.py`, and checked in the failing direction (see the correction below). |

Two of those were **not** clean on the first pass and were re-measured before being
recorded, which is the reason this section exists at all:

- The first contrast script reported 20 failures at 2.07:1. It read each element's own
  `background-color`, which is `rgba(0,0,0,0)` on transparent nodes, so it compared
  text against black. Walking up to the first painted ancestor gives **0 failures**.
  The number was a measurement artifact, not a design defect.
- The first focus check called `el.focus()` programmatically. Chrome does not apply
  `:focus-visible` to scripted focus, so "outline-style: none" looked like a missing
  ring. Real `Tab` presses do match `:focus-visible`, and most controls show the ring.
  One class of control genuinely does not — see finding 1.

*(Corrected 2026-10-04, same day, by the gates written from this audit. Two more
artifacts of the same kind turned up while those gates were being built, and both
were recorded here as product findings before they were checked properly:*

- *Sampling the ring immediately after `Tab` reads a **transition frame**. The
  controls animate (`transition: all`), so at 0ms the outline computes as the UA
  default (3px `#45413A`) and only settles on the token (2px `#b45309`) after
  ~150ms. That sample was briefly written up as an `--accent`/`--focus` token
  collision between the ported sheet and the Tailwind theme. There is no collision:
  measured settled, the ring is exactly `2px solid rgb(180, 83, 9)`, which is
  `--accent` and what `DESIGN.md:46` specifies.*
- *Asserting `outlineStyle` specifically called six controls failures — `#attach`,
  `#go`, a rail tick, a bare anchor — that all draw their ring with `box-shadow`,
  which is how this sheet does it globally (`:focus-visible { box-shadow: var(--focus) }`)
  with an outline added only on the classes whose own reset outranks it. A real
  indicator through **either** channel counts; the gate now measures both, and was
  checked in the failing direction by injecting
  `:focus-visible { outline: none !important; box-shadow: none !important }` — 0 of 12
  controls pass under that sabotage, 11 of 11 pass as shipped.*)


## Findings

### 1. Suggestion chips lose the focus ring — violates the repo's own rule (Medium)

`DESIGN.md:46`: *"`:focus-visible` = 2px orange ring, everywhere, no exceptions."*
Measured with real `Tab` presses at 390px: the two question chips
("Why is the Bluepea…", "What credit do we…") report
`matchesFocusVisible: true` with `box-shadow: rgba(0,0,0,0) 0px 0px 0px 0px` —
keyboard users get **no indicator**, while neighbouring buttons do.
Owner: the suggestion-chip buttons in `frontend/src/App.tsx` (they carry a class that
overrides the ring, or lack the shared focus utility).
Verify after fix: tab to a chip and assert a non-transparent `box-shadow`.

*(Fixed before this line was written, and now gated: `frontend/src/legacy/deck.css`
names the classes whose reset outranked the global rule, so `.chip:focus-visible`
computes `outline: solid 2px rgb(180,83,9)` plus the accent `box-shadow` — measured at
both 1280px and 390px. `check_ui_react.py` asserts the ring on **every** control the
keyboard reaches rather than on chips specifically, because the chip row is
`display:none` once a thread has turns (`body.chatti`) and a chip-pinned gate timed out
on a restored chat — correct product behaviour, wrong precondition.)*

### 2. Touch targets below 44px across the sidebar (Medium)

Apple HIG / Material minimum is 44×44pt / 48×48dp; the skill lists this as CRITICAL
priority-2. Measured at 390×844: nav rows render **243×38**, the hamburger **38×38**,
and the collapse control **26×26**. Content is reachable but easy to mis-tap, and the
smaller ones are icon-only.
Owner: sidebar/nav row padding in `frontend/src/components/Sidebar.tsx` and
`frontend/src/App.tsx`. Either raise the row height to ≥44px or extend the hit area
with padding/negative-margin so the visual density is preserved.

### 3. No `main` landmark (Low-Medium)

`DESIGN.md:103` lists "Landmarks, skip link, aria labels…" as an accessibility
requirement, and a skip link exists (measured: a 1×1 visually-hidden "Skip to chat").
But no `<main>` or `role="main"` exists anywhere in `frontend/src` — so the skip link
has no landmark to skip *to*, and screen readers get no main region.
Owner: the app shell (`frontend/src/App.tsx`) around the conversation/graph panes.

*(Fixed: `#kestrel-main` carries `role="main"`, and the gate asserts the skip link's
target exists **and** is a main landmark — so the link can no longer point at nothing.)*

### 4. 19 raw hex literals in components — violates rule 1 (Medium)

*(Corrected 2026-10-04: the count is right, the finding is mostly wrong. Of the 19,
**16 sit inside `appearanceProps()` (`Animations.tsx:368-405`) and are Clerk
`appearance.variables`** — Clerk consumes those as literal CSS custom-property values
in its own stylesheet and cannot be handed a Tailwind token, so migrating them would
break the sign-in theme rather than fix anything. Three are genuine and small: a
`linear-gradient(155deg,#f49d54,#d96f1f 78%)` and a `#161616` at `Animations.tsx:416`
and `:419`. The COR-13 argument in this section's last sentence does not apply to the
Clerk block either — those variables are already selected per theme by the `light`
branch above them, which is why 16 of them exist in two sets.)*

`DESIGN.md:108`: *"No raw hex in components — use token utilities."* Counted in
`frontend/src`: **18 in `components/Animations.tsx`, 1 in `App.tsx`** (excluding
`index.css`, where the token definitions legitimately live). Per-token colour in
components means these do not respond to `data-theme` swaps, which is how the "light
theme keeps dark-theme colors" defect (Round 1, COR-13) happened in the first place.
Owner: `Animations.tsx` — move those colours onto `var(--…)` tokens.

### 5. Text glyphs used as icons next to an SVG icon set (Low)

`☰`, `✕`, `«` appear as control text in `App.tsx`, `Animations.tsx`,
`Sidebar.tsx` and `static/shell.js`, while the rest of the product uses Lucide SVGs.
The skill's `icon-style-consistent` / `no-emoji-icons` rules exist because glyphs
render differently per font and cannot be token-styled. Low severity, but it is the
kind of inconsistency that reads as "unfinished" rather than as a bug.

### 6. Micro-labels at 9.5–10px with no documented floor (Low)

Four painted text nodes measure 9.5–10px (uppercase eyebrow labels like the
`text-[10.5px]` family). The skill's rule is ≥12px for body text; these are labels, so
this is a judgement call — but `DESIGN.md` sets **no minimum size at all**, which is
why the codebase drifts. Cheapest durable fix: state a floor in `DESIGN.md` §type, then
raise or accept deliberately.

## Found after this audit was written, by the gates it produced

The audit's own recommendation ("a browser gate that asserts them is worth doing
before the fixes scatter again") was taken up the same day, and the gates found three
things the eyeball pass had missed. All three are fixed and gated.

### 7. The "you are here" rail tick has no focus indicator (Medium)

`#rail .tick.here` (`frontend/src/legacy/shell.css:160`) carries a resting amber glow
at specificity 1-2-0, which outranks the sheet's global `:focus-visible` rule — so
tabbing onto a rail tick changed **nothing** on screen. This is a WCAG 2.4.7 failure on
a real navigation control, and it was invisible to review because the control is 2.5px
tall and nobody tabs to it deliberately. Fixed with an explicit
`#rail .tick:focus-visible { outline: 2px solid var(--accent); outline-offset: 3px }`.

### 8. A deploy left open tabs on a silent blank page (High)

`ops/build_frontend.sh` replaces the hashed bundle and deletes the previous one, so a
tab still holding the old `index.html` requests files that answer 404. React never
mounts, and the user gets a dark empty page with no message and nothing in the address
bar to explain it. Measured, not theorised — the live server log recorded exactly this:

```
"GET /assets/index-SSCQYO2q.js HTTP/1.1" 404 Not Found
"GET /assets/index-m876h3li.css HTTP/1.1" 404 Not Found
"GET /assets/Markdown-anNGsjxq.js HTTP/1.1" 404 Not Found
```

`/` already sends `cache-control: no-cache, must-revalidate`, so this is not a header
bug — a tab restored from bfcache, or one that was open across the restart, still asks
for the hashes it was given. Fixed in `frontend/index.html`: a script or chunk that
fails to load reloads the tab once (so it picks up the new manifest), and if a reload
does not fix it, renders a `role="alert"` panel with a Reload button instead of nothing.
Gated by the `stale bundle` section, which 404s `/assets/index-*.js` and asserts the
message appears. Healthy loads are unaffected: one navigation, no loop, and the
session flag is cleared as soon as `#root` has children.

### 9. An unhandled crash answered in a shape the client cannot read (Medium)

Starlette's default 500 body is the plain text `Internal Server Error`, while every
deliberate error in `app.py` is `{"detail": …}` — and `frontend/src/lib/api.ts:111`
reads failures with `res.json().catch(() => null)`. So a server-side crash produced no
server message at all, only the bare `HTTP 500` fallback, which is exactly the case
where the user most needs a sentence. Fixed with an `@app.exception_handler(Exception)`
that logs the traceback and returns the same `{detail}` shape; `HTTPException` still
goes through FastAPI's handler first, so the 409/410/413/503 contract is untouched.
Verified by raising a deliberate error through the ASGI app: `500`,
`application/json`, `{"detail": "Something went wrong on our side…"}`.
