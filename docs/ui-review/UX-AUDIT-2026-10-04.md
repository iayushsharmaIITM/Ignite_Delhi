# UI/UX audit — served React app (2026-10-04)

Lens: `ui-ux-pro-max-skill:ui-ux-pro-max` (8-pillar priority table + the §1–§3
CRITICAL checks), measured against the project's own **`DESIGN.md`** contract rather
than a recommended style — the repo already owns its design system, so its rules are
the standard and the skill supplies the check categories.

Method: the **committed bundle** was served by a local mock tier (`:8025`,
`PROVIDER=mock`, `AUTH_MODE=off`, `KESTREL_UI=react`) and driven in a real browser at
1440×1000 and 390×844, computing contrast in-page against each element's *actual
painted ancestor background*. The measurement script was a throwaway in `/tmp`; it is
not committed, because a UI-contrast gate needs the app's own theme fixtures before it
can be trusted to stay green.

Not covered: signed-in Clerk UX, streaming feel, and anything requiring the cloud
brain — none of those are reachable without the owner's session.

## What measured clean

| Check | Result |
|---|---|
| Horizontal scroll at 390px | none — `scrollWidth 390 == clientWidth 390` |
| Body-text contrast (WCAG 4.5:1) | **0 failures of 32** painted text nodes |
| Icon-only controls without a label | **0** — every unlabeled control carries `aria-label`/`title` |
| Heading hierarchy | one `h1`, no level skips |
| Reduced motion | honoured — 2 `prefers-reduced-motion` blocks in the served CSS, source `frontend/src/index.css:135` |
| Keyboard focus ring | visible on the controls that define it (orange `box-shadow` ring) |

Two of those were **not** clean on the first pass and were re-measured before being
recorded, which is the reason this section exists at all:

- The first contrast script reported 20 failures at 2.07:1. It read each element's own
  `background-color`, which is `rgba(0,0,0,0)` on transparent nodes, so it compared
  text against black. Walking up to the first painted ancestor gives **0 failures**.
  The number was a measurement artifact, not a design defect.
- The first focus check called `el.focus()` programmatically. Chrome does not apply
  `:focus-visible` to scripted focus, so "outline-style: none" looked like a missing
  ring. Real `Tab` presses do match `:focus-visible`, and most controls show the ring.
  One class of control genuinely does not — see finding 1.

## Findings

### 1. Suggestion chips lose the focus ring — violates the repo's own rule (Medium)

`DESIGN.md:46`: *"`:focus-visible` = 2px orange ring, everywhere, no exceptions."*
Measured with real `Tab` presses at 390px: the two question chips
("Why is the Bluepea…", "What credit do we…") report
`matchesFocusVisible: true` with `box-shadow: rgba(0,0,0,0) 0px 0px 0px 0px` —
keyboard users get **no indicator**, while neighbouring buttons do.
Owner: the suggestion-chip buttons in `frontend/src/App.tsx` (they carry a class that
overrides the ring, or lack the shared focus utility).
Verify after fix: tab to a chip and assert a non-transparent `box-shadow`.

### 2. Touch targets below 44px across the sidebar (Medium)

Apple HIG / Material minimum is 44×44pt / 48×48dp; the skill lists this as CRITICAL
priority-2. Measured at 390×844: nav rows render **243×38**, the hamburger **38×38**,
and the collapse control **26×26**. Content is reachable but easy to mis-tap, and the
smaller ones are icon-only.
Owner: sidebar/nav row padding in `frontend/src/components/Sidebar.tsx` and
`frontend/src/App.tsx`. Either raise the row height to ≥44px or extend the hit area
with padding/negative-margin so the visual density is preserved.

### 3. No `main` landmark (Low-Medium)

`DESIGN.md:103` lists "Landmarks, skip link, aria labels…" as an accessibility
requirement, and a skip link exists (measured: a 1×1 visually-hidden "Skip to chat").
But no `<main>` or `role="main"` exists anywhere in `frontend/src` — so the skip link
has no landmark to skip *to*, and screen readers get no main region.
Owner: the app shell (`frontend/src/App.tsx`) around the conversation/graph panes.

### 4. 19 raw hex literals in components — violates rule 1 (Medium)

`DESIGN.md:108`: *"No raw hex in components — use token utilities."* Counted in
`frontend/src`: **18 in `components/Animations.tsx`, 1 in `App.tsx`** (excluding
`index.css`, where the token definitions legitimately live). Per-token colour in
components means these do not respond to `data-theme` swaps, which is how the "light
theme keeps dark-theme colors" defect (Round 1, COR-13) happened in the first place.
Owner: `Animations.tsx` — move those colours onto `var(--…)` tokens.

### 5. Text glyphs used as icons next to an SVG icon set (Low)

`☰`, `✕`, `«` appear as control text in `App.tsx`, `Animations.tsx`,
`Sidebar.tsx` and `static/shell.js`, while the rest of the product uses Lucide SVGs.
The skill's `icon-style-consistent` / `no-emoji-icons` rules exist because glyphs
render differently per font and cannot be token-styled. Low severity, but it is the
kind of inconsistency that reads as "unfinished" rather than as a bug.

### 6. Micro-labels at 9.5–10px with no documented floor (Low)

Four painted text nodes measure 9.5–10px (uppercase eyebrow labels like the
`text-[10.5px]` family). The skill's rule is ≥12px for body text; these are labels, so
this is a judgement call — but `DESIGN.md` sets **no minimum size at all**, which is
why the codebase drifts. Cheapest durable fix: state a floor in `DESIGN.md` §type, then
raise or accept deliberately.

## Suggested order

3 → 1 → 2 → 4 → 6 → 5. Landmark and focus ring are small, strictly correctness fixes;
the touch-target pass is a visual-density decision; the hex migration belongs with any
future light-theme work. Items 1–4 are all measurable in the served bundle, so a
browser gate that asserts them (extending `check_ui_react.py`) is worth doing before
the fixes scatter again — the same lesson as Round 3: a check that never ran is worse
than no check, because it reads as covered.
